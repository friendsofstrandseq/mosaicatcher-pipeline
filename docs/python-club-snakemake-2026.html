What’s a workflow manager?

Three properties

  • Declarative — describe what should exist (the outputs), not how to get there step by step.
  • DAG-based — the tool figures out the dependency graph and what’s stale.
  • Portable — same workflow definition runs on laptop / SLURM / Kubernetes / AWS Batch. Executor is configuration, not code.

Anchor these three properties — every later slide is a consequence of one of them.

FAIR principles → workflow managers

Accessible Git-hosted · containers/conda bundled · reproducible by anyone
Interoperable Same workflow laptop → SLURM → cloud · standard reports

FAIR was originally about data. The WorkflowHub / nf-core / Snakemake communities adopted it for workflows.

Snakemake core, in 3 minutes

The object model — one rule, four ideas

rule align:
    input:  "fastq/{sample}.fq.gz"      # wildcards
    output: "bam/{sample}.bam"
    threads: 8
    resources: mem_mb=16_000, runtime=120
    conda:  "envs/bwa.yaml"             # per-rule software
    shell:  "bwa mem -t {threads} ref {input} | samtools sort -o {output}"

A Snakefile is just Python with extra top-level constructs. Highlight: rule, wildcards, resources, per-rule env.

Pull-based DAG (Make-style)

flowchart LR
    A[fastq/A.fq.gz] --> B[align A]
    B --> C[bam/A.bam]
    C --> D[call_variants A]
    D --> E[vcf/A.vcf]
    style A fill:#e3f2fd,stroke:#1565c0
    style C fill:#fff9c4,stroke:#f9a825
    style E fill:#c8e6c9,stroke:#2e7d32

You ask for vcf/A.vcf. Snakemake recurses back: “what do I need? which rule produces it?” until it hits files that exist.

--dry-run shows the whole plan before anything executes.

This is the single most important concept. It shows up again as the deepest semantic difference vs Nextflow.

Reproducibility primitives

  • conda: / container: per rule
  • --report report.html — single-file shareable provenance
  • .snakemake/ tracks code, params, inputs, env hashes → smart rerun

v7 → v8 → v9: what changed

The headline

v8 (Jan 2024) was the disruption.

v9 (Feb 2025) is mostly invisible.

The whole engine was decomposed into a plugin framework.

Each plugin is pip install-able. Settings declared as @dataclass, become CLI flags automatically.

Executor plugins — how it looks

pip install snakemake-executor-plugin-slurm
snakemake --executor slurm --jobs 100 ...

Available officially (late 2025): slurm, lsf, htcondor, kubernetes, googlebatch, azure-batch, flux, cluster-generic

Catalog: https://snakemake.github.io/snakemake-plugin-catalog/

SLURM plugin submits Snakemake itself as the job script — necessary so run: blocks and wrappers work remotely. Installing the executor plugin also installs a companion jobstep plugin used on the worker.

Storage plugins — the storage directive

v7 — imports inside Snakefile

from snakemake.remote.S3 \
    import RemoteProvider
S3 = RemoteProvider()

rule x:
    input: S3.remote(
        "bucket/in.txt")

v8/v9 — directive

storage:
    provider="s3",
    max_requests_per_second=10

rule x:
    input: storage(
        "s3://bucket/in.txt")

Or workflow-wide: --default-storage-provider s3 --default-storage-prefix s3://bucket/

HPC-critical plugin: snakemake-storage-plugin-fs — stages data between shared FS and local scratch. See HPC section.

Software deployment unified

v7

--use-conda
--use-singularity
--use-envmodules
--conda-frontend mamba

v8/v9 — one flag

--sdm conda
--sdm apptainer
--sdm conda apptainer
--sdm env-modules
  • --conda-frontend mamba gone — libmamba is the default solver.
  • Roadmap: software-deployment will itself become a plugin (Pixi backend on the way).

Reports got nicer

  • category / subcategory / labels as functions of wildcards → per-sample dynamic labelling
  • Automatic toggle switches when items differ on one labelled dimension
  • First-class Datavzrd embedding via report(directory(...))
  • --report-stylesheet custom.css for branding
  • --report-after-run auto-generates on success (9.x)

What’s actually new in v9?

“Between Snakemake 8 and Snakemake 9, there is only a single breaking change in how custom loggers are provided, such that hardly any user should be affected.”

— official migration guide

The change: logger plugins (snakemake-logger-plugin-<name>)

Motivation: v7/v8 synchronous log handlers could crash workflows on monitoring-backend hiccups.

First plugin: snakemake-logger-plugin-snkmt (SQLite/observability backend).

v7 → v8 migration footguns

  • dynamic() outputs → use checkpoints
  • version: directive removed → use conda: / container:
  • subworkflow: removed → use module: + use rule * from foo as foo_*
  • from snakemake.remote.* → storage directive
  • Profiles must be updated (dead flags)
  • CI must pip install snakemake-executor-plugin-slurm explicitly
  • NCBI / EGA remote providers → became wrappers, not storage plugins
  • ⚠ 9.20 (May 2026): runtime profile values now in minutes, not seconds — audit profiles

All of these surfaced in MosaiCatcher CI. The CI install step is the most common silent failure.

Snakemake vs Nextflow

Framing slide

No “which is better”.

Compare on technical primitives,

pick on fit, not on taste.

Set the tone explicitly. Both are mature, both run in production at EMBL.

The deepest difference: dataflow model

Snakemake — pull

  • Target-driven (Make-style)
  • You request an output file
  • Tool recurses back: “what do I need?”
  • Bottoms out at existing inputs
  • Mental model: “what file do I want?”

Nextflow — push

  • Channel-driven (Kahn / CSP / dataflow)
  • processes connected by channels
  • Values flow asynchronously
  • A process fires when each input channel has a record
  • Mental model: “what stream into what process?”

This explains every other downstream difference. Spend a beat here.

DAG construction

Snakemake

  • Static, up-front
  • --dry-run shows the full plan
  • --dag / --rulegraph → Graphviz
  • Conditional flow via Python (input functions)
  • Checkpoints when output contents drive downstream inputs

Nextflow

  • Dynamic, at runtime
  • Channels evaluated lazily as records arrive
  • Scatter/gather from operators (splitFastq, groupTuple)
  • -preview, -with-dag are approximations
  • True graph only exists once channels emit

Language & tooling

Snakemake Nextflow
Host language Python-embedded DSL Groovy DSL2 on the JVM
Runtime CPython Java 17+ (since 25.04, May 2025)
Debugging pdb + --debug + --printshellcmds log-driven via work/.command.{sh,log}
IDE Python ecosystem + snakefmt Seqera VS Code Nextflow Language Server

Myth-buster

“Nextflow needs Java” — true. Specifically Java 17+ since Nextflow 25.04 (May 2025). Java 11 is no longer supported.

Resume / cache — the myth-buster slide

Snakemake

  • File timestamps + tracked metadata (.snakemake/)
  • Rerun triggers: mtime, params, input, software-env, code
  • Configurable: --rerun-triggers ...
  • Make pitfall: touching an input invalidates downstream

Nextflow

  • Hash in .nextflow/cache/<session>/ (LevelDB)
  • Hashes script body, input values, file attributes (path/size/mtime) — not contents by default
  • cache 'deep' → true content hash
  • cache 'lenient' → relaxed for shared FS
  • Debug: -dump-hashes

Myth-buster

“Nextflow -resume is content-hashed, immune to mtime issues” — partially false. Default is file attributes (incl. mtime); content hashing is opt-in via cache 'deep'. Shared-FS mtime jitter is a documented cause of spurious cache misses.

When does each shine?

Snakemake fits when…

  • Team is Python-native
  • Pipeline is target / file-driven
  • Debugging needs interactive Python
  • You want the DAG up front
  • One Snakefile readable end-to-end

Nextflow fits when…

  • Team has Java/Groovy/Scala people
  • Pipeline is stream / event-driven
  • AWS Batch / Fusion matter
  • You want nf-core off-the-shelf

EMBL HPC: 5 things to check

The 5-point checklist

  1. Throttle scheduler submissions — max-jobs-per-second: 10
  2. Stage compute through scratch — default-storage-provider: fs + local-storage-prefix: /scratch/$USER/<wf>
  3. Remove input-output from shared-fs-usage — otherwise step 2 is bypassed
  4. Enable Snakemake output cache — SNAKEMAKE_OUTPUT_CACHE=/scratch_cached/<group>/snakemake_cache
  5. Share conda + apptainer caches — group-writable parallel FS, setgid bit (chmod 2775)

Full draft in docs/hpc-pipeline-optimization_ongoing.md (1241 lines). These 5 are highest impact.

The whole story in 5 lines

profile/config.yaml
executor: slurm
default-storage-provider: fs
local-storage-prefix: /scratch/$USER/snakemake_test/local
slurm-efficiency-report: true
max-jobs-per-second: 10

That’s it. Everything else is per-rule resources.

Storage tier cheat sheet

Data type Tier Why
Reference genomes Cached parallel FS Read 100× during alignment
BAM / CRAM intermediates Parallel FS High-throughput sequential writes
Computed indexes (BWA, STAR) Cached parallel FS Repeated reads, expensive to rebuild
conda / container caches Parallel FS Shared across users
Temp / sorting buffers Local scratch Ultra-fast, job-local

Common pitfalls

  • Stale .snakemake/ locks when two users share a checkout → per-user --workflow-profile
  • Conda env build races → pre-build with --conda-create-envs-only, share conda-prefix
  • $JOBID not expanded in scratch paths → upgrade to Snakemake 9.3.4+
  • --conda-frontend mamba in profile → warning on v8, error on v9, just delete it
  • Old v7 --cluster "sbatch ..." in CI → silently broken on v8, replace with --executor slurm
