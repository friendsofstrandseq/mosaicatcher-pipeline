From a script to a Snakefile

Same intent — align each FASTQ, call variants per sample, merge into a cohort VCF. The script hard-codes the loop; the Snakefile declares the dependencies and lets Snakemake build the DAG.

  Bash-style pseudo-script 

for S in A B C; do
  bwa mem ref fq/$S.fq.gz \
    | samtools sort -o bam/$S.bam
  gatk HaplotypeCaller \
    -I bam/$S.bam -O vcf/$S.vcf
done

bcftools merge \
  vcf/A.vcf vcf/B.vcf vcf/C.vcf \
  > vcf/cohort.vcf

Linear · no parallelism · re-runs everything · no provenance.

  Snakefile 

SAMPLES = ["A", "B", "C"]

rule all:
    input: "vcf/cohort.vcf"

rule align:
    input:  "fq/{s}.fq.gz"
    output: "bam/{s}.bam"
    shell:  "bwa mem ref {input} | samtools sort -o {output}"

rule call:
    input:  "bam/{s}.bam"
    output: "vcf/{s}.vcf"
    shell:  "gatk HaplotypeCaller -I {input} -O {output}"

rule merge:
    input:  expand("vcf/{s}.vcf", s=SAMPLES)
    output: "vcf/cohort.vcf"
    shell:  "bcftools merge {input} > {output}"

Parallel by default · resumable · per-rule env · DAG up-front.

A rule — zoom in

A pipeline is organised as a list of rules. Each rule is one step — e.g. align FASTQs, call variants, build a plot — declared by its inputs, outputs and how to produce one from the other.

Wildcards
inferred from targets
Params
non-file config
Resources
cpu · mem · runtime
Env per rule
conda · container · module 
rule align:
    input:   "fastq/{sample}.fq.gz"          # wildcards: {sample}
    output:  "bam/{sample}.bam"
    log:     "logs/{sample}.log"
    params:  min_mapq = 30                   # → {params.min_mapq}
    threads: 8
    resources: mem_mb=16_000, runtime=120    # SLURM-aware
    conda:   "envs/bwa.yaml"                 # or container: / envmodules:
    shell:
        "bwa mem -t {threads} ref {input} | "
        "samtools view -q {params.min_mapq} -b - | "
        "samtools sort -o {output} 2> {log}"

Conditional execution — checkpoints

Pattern. Step 1 produces an actionable verdict (a table, a pass/fail list). Step 2 must only run on the survivors — the DAG branches that should never execute are pruned at runtime.

# upstream — produce per-cell counts
rule count_cell:
    input:  "bam/{cell}.bam"
    output: "counts/{cell}.tsv"

# checkpoint — score every cell, write a verdict table
checkpoint filter_cells:
    input:  expand("counts/{cell}.tsv", cell=ALL_CELLS)
    output: "qc/verdict.tsv"           # columns: cell, keep(bool)
    script: "scripts/qc_filter.py"

# per surviving cell (normal rule)
rule call_sv:
    input:  "counts/{cell}.tsv"
    output: "sv/{cell}.calls.tsv"

# input function — .get() blocks on the checkpoint, then
# the DAG is re-evaluated with only the cells we keep
def passing(wildcards):
    verdict = checkpoints.filter_cells.get().output[0]
    kept = pd.read_table(verdict).query("keep").cell
    return expand("sv/{cell}.calls.tsv", cell=kept)

rule collect:                          # ◀ consumes the function
    input:  passing
    output: "sv/all_calls.tsv"

  Replaces legacy dynamic() — removed in v8.

The checkpoint emits the verdict; the input function then prunes the per-cell edges — they are discovered at runtime, not declared up-front.

Conda + container — two ways to combine

  Ad hoc — conda inside a global container

A global container: statement (top of the Snakefile) + per-rule conda: → Snakemake enters the container, then builds the env inside it:

# top of the Snakefile (global, not per-rule)
container: "docker://condaforge/miniforge3"

rule call_snvs:
    conda: "envs/gatk.yaml"
    shell: "gatk HaplotypeCaller ..."
snakemake --sdm conda apptainer

Pinned OS and pinned packages, no bespoke image to build. Env hash includes the image URL.

  Bake — --containerize all envs into one image 

snakemake --containerize > Dockerfile
docker build -t myorg/mc:2.5.0 .

Then pin the workflow to that prebuilt image:

# top of the Snakefile
containerized: "docker://myorg/mc:2.5.0"

rule call_snvs:
    conda: "envs/gatk.yaml"   # baked in
    shell: "gatk HaplotypeCaller ..."

One image holds all envs → no per-node solves; ship to CI / air-gapped HPC; reproducible to the byte.

Driving Snakemake from Python — the API

Since v8 the engine is importable — no subprocess, no CLI string. Snakemake becomes a library you embed in a larger stack (a service, a watcher, a Nextflow-style orchestrator, a notebook):

from snakemake.api import (
    SnakemakeApi, OutputSettings, ResourceSettings,
    ConfigSettings, DeploymentSettings, DeploymentMethod,
    DefaultResources, DAGSettings, ExecutionSettings,
)

with SnakemakeApi(OutputSettings(dryrun=False)) as api:
    wf = api.workflow(
        resource_settings=ResourceSettings(
            nodes=150,
            default_resources=DefaultResources(["mem_mb=500"]),
        ),
        config_settings=ConfigSettings(config={"samples": new_run}),
        deployment_settings=DeploymentSettings(
            deployment_method={DeploymentMethod.CONDA,
                               DeploymentMethod.APPTAINER},
        ),
        snakefile=PIPELINE / "workflow" / "Snakefile",
        workdir=PIPELINE,
    )
    dag = wf.dag(dag_settings=DAGSettings(force_incomplete=True))
    dag.execute_workflow(executor="slurm", ...)   # SLURM settings

Snakemake as an engine

  • watcher — auto-launch on new data landing
  • web service / REST — run pipelines on request
  • orchestrator step — a node inside a bigger DAG
  • notebook — drive runs interactively, inspect the DAG

The CLI is just a thin wrapper over these *Settings objects — anything the CLI does, you can do programmatically.

Compose storage and compute

One workflow, many backends — each rule’s inputs/outputs can sit on a different storage, and each rule can run on a different executor.

Plugin catalog · scheduler — firstfit

What. Replaces the default ILP scheduler with a first-fit-decreasing heuristic — faster scheduling on workflows with thousands of jobs (ILP can stall on the DAG-search step).

pip install snakemake-scheduler-plugin-firstfit
snakemake --scheduler firstfit --jobs 5000

  Trade-off: faster scheduling decisions, less globally optimal packing than ILP. Worth it once the ILP overhead dominates the actual job runtime.

plugins/scheduler/firstfit

Stability & backward-compatibility — issues to watch

The engine moves faster than user pipelines. Same Snakefile, different minor → sometimes different behaviour.

  Removed / renamed

  • dynamic() outputs → checkpoints
  • version: directive → conda: / container:
  • subworkflow: → module: + use rule …
  • from snakemake.remote.* → storage directive
  • v7 profiles silently broken on v8 (removed flags)

CI / containers — list every plugin explicitly (snakemake-executor-plugin-slurm, …) or --executor slurm exits with plugin not found.

  Real case — mosaicatcher

Sequential checkpoints — e.g. mosaic_count → summarise_ploidy → filter_bad_cells — exercise the DAG-reevaluation path harder than most pipelines.

v8 — never reached a working state for our chained checkpoints (DAG re-eval bug on the second checkpoint).
v9 — works · but some 9.x point releases silently regress on the same DAG (e.g. group jobs + checkpoint interactions) → we pin a known-good range.

  Lesson: treat the engine like a dependency — pin snakemake==9.X.Y, pin every plugin, gate upgrades on the full test matrix.

1 · Caching — workflow + containers

  Workflow output cache 

export SNAKEMAKE_OUTPUT_CACHE=\
  /scratch_cached/<group>/snakemake_cache

Per rule:

rule index_ref:
    output: "ref.fa.bwt"
    cache: True   # → goes into $SNAKEMAKE_OUTPUT_CACHE

The hash key includes input file content, rule code, params, software-env, version. As long as the recipe is identical, user B reuses what user A built — even from a different working tree.

Concretely: BWA index on hg38 ≈ 1 h CPU · STAR index ≈ 1.5 h · gnomAD VCF tabix ≈ 30 min. Build once per group, not once per user.

  Container cache 

# profile
apptainer-prefix: /scratch_cached/<group>/apptainer

  On /scratch_cached (same fast tier as the workflow cache) → image pulled once for the whole group.

  Pre-pull manually: apptainer pull --dir $APPTAINER_CACHEDIR docker://... (no Snakemake “container-prewarm” flag exists — first job pulls).

  Skip the cache entirely when EESSI covers the tool — envmodules: loads from CernVM-FS, no image pull, no conda solve.

2 · Storage — what the fs plugin actually does

The fs storage plugin treats a local filesystem path as a “remote” storage backend. Snakemake stages inputs in to a fast per-job location before the job runs, then stages outputs back when it finishes — same code path as S3/GCS storage plugins, but the “remote” is just another POSIX mount.

shared FS (slow) → stage-in → local scratch (fast) → run → stage-out → shared FS

profile/config.yaml
executor: slurm
default-storage-provider: fs              # use fs as backend
local-storage-prefix: /scratch/$USER/wf   # per-job staging dir
remote-job-local-storage-prefix: /tmp/$USER/wf

shared-fs-usage:           # what stays on shared FS, not staged
  - persistence            # .snakemake/ metadata
  - software-deployment    # conda/apptainer
  - sources                # the Snakefile itself
  # input-output absent → staged through fs plugin

Why bother

  • Compute nodes hammer local NVMe, not the shared parallel FS — no metadata storms.
  • Same plugin contract as s3 / gcs → swap backends without changing rules.
  • Inputs are copied, not symlinked → safe with temp() cleanup.

CLI: --default-storage-provider · --local-storage-prefix · --shared-fs-usage · plugins/storage/fs

4 · Job arrays — pack 1-CPU tasks into one SLURM submission

profile/config.yaml
executor: slurm
slurm-array-jobs: all       # all eligible rules
slurm-array-limit: 1000     # tasks / array

# pack 10 single-CPU jobs into one array
group-components:
  - count_cell=10

For a per-cell rule that needs 1 CPU each:

rule count_cell:
    input:  "bam/{cell}.bam"
    output: "counts/{cell}.tsv"
    threads: 1
    group:   "count_cell"     # ← the array

What lands on SLURM:

$ squeue -u $USER
JOBID         NAME       NCPUS  ST
12345_[1-10]  count_cell    1   PD
# 1 sbatch · 10 tasks · 1 cpu each
# SLURM sees a 10-cpu allocation
  1 sbatch · 10 array tasks · 10 cpus total
task 11 cpu · cell A
task 21 cpu · cell B
task 31 cpu · cell C
……
task 101 cpu · cell J

  In theory: big win for many short 1-CPU jobs (per-cell QC, per-chrom split) — one scheduler decision instead of N.

  In practice (our setup): parallelism is lost. The 10 tasks inside the group ran sequentially in the same allocation — same wallclock as N separate jobs, no speed-up. Test on your cluster.

  Heterogeneous resources → don’t mix into one array.

5 · EESSI — env-modules with native optimisation

EESSI = European Environment for Scientific Software Installations — a CernVM-FS stream of EasyBuild-compiled scientific software, dispatched per microarchitecture (zen3, icelake, haswell …), mountable on any HPC.

Bootstrap once 

source /cvmfs/software.eessi.io/versions/2023.06/init/bash
module load BWA SAMtools STAR

Use per rule 

rule align:
    envmodules: "BWA/0.7.17", "SAMtools/1.18"
    shell: "bwa mem ... | samtools sort ..."
snakemake --sdm env-modules ...
  Fast — no conda solve, no image pull · first job runs immediately
  Optimised — CPU-tuned binaries → wallclock wins on AVX-heavy tools
  Portable — identical versions across any HPC mounting /cvmfs
  Reproducible — comparable to containers, no I/O overhead
  Cheap — zero per-user env duplication → group quota saved

6 · Job optimisation — efficiency report

The SLURM executor emits a per-rule CPU & memory utilisation report at the end of each run — read it to right-size set-resources: (rules that ask for 32 GB but use 2 GB, or run at 20% CPU).

profile/config.yaml
slurm-efficiency-report:       true
slurm-efficiency-report-path:  efficiency.txt
slurm-efficiency-threshold:    0.8        # flag rules below 80%

run → efficiency report → tune set-resources → cheaper next run

Dataflow paradigm — pull vs push

fq/{s}.fq.gz — align → bam/{s}.bam — call → vcf/cohort.vcf

  Snakemake — pull

Start from the target file, walk back to inputs.

rule all:
    input: "vcf/cohort.vcf"   # ◀ the target

rule call:
    input:  "bam/{s}.bam"
    output: "vcf/{s}.vcf"

rule align:
    input:  "fq/{s}.fq.gz"    # ◀ leaf
    output: "bam/{s}.bam"
snakemake vcf/cohort.vcf --cores 8

Static DAG, resolved before anything runs.

  Nextflow — push

Start from the source channel, flow forward.

workflow {
  reads = Channel.fromFilePairs(
    'fq/*_{1,2}.fq.gz'        // ◀ the source
  )
  ALIGN(reads) | CALL | view
}

process ALIGN { /* fq → bam */ }
process CALL  { /* bam → vcf */ }
nextflow run main.nf -resume

Dynamic DAG, materialised as channels emit.

Resume / cache — what actually invalidates

  “My input / code / container changed. Will the job rerun?”

  Snakemake — --rerun-triggers

Signal Default
mtime of inputs ✅
input set (paths) ✅
params value ✅
code of rule body ✅
software-env hash ✅

Each trigger is named & opt-out-able: --rerun-triggers mtime params input.

  Sensitive in dev. Touching code / params during iteration reruns every downstream job — pin --rerun-triggers mtime while iterating.

  Nextflow -resume

Signal Default cache 'deep'
path + size + mtime ✅ path+size
file SHA-256 — ✅
script: body ✅ ✅
container: ID ✅ ✅
ext directive ✅ ✅
other directives ❌ * ❌ *
  • unless referenced in script: body via ${task.…}. NF hashes code, container & ext; “all content-hashed” still false — file content needs cache 'deep'.

  Bottom line. Default invalidation surfaces are comparable. Differences: Snakemake exposes each trigger by name for opt-out; Nextflow re-hashes if any referenced directive value moves; file content needs cache 'deep' (NF) or explicit --rerun-triggers mtime opt-out (SMK).

  Build on demand — Wave
  POSIX over object storage — Fusion

Wave — Seqera’s container-provisioning service. Takes a conda spec attached to a process, builds an OCI container on demand with that environment, caches it in a registry. Supports amd64 + arm64. Apache-2.0, open source.

Fusion — a virtual POSIX layer that lets processes read/write S3, GCS or Azure Blob as if they were a mounted directory. Avoids stage-in/stage-out copies on cloud. Commercial, part of Seqera Platform.

When does each fit?

  Snakemake fits when…

  • Team is Python-native
  • Pipeline is file / target-driven
  • You want the DAG up-front
  • Debugging needs interactive Python
  • One Snakefile, readable end-to-end

  Nextflow fits when…

  • Team has Groovy / JVM people
  • Pipeline is stream / event-driven
  • AWS Batch or Fusion matter
  • You want nf-core off-the-shelf
  • You want Seqera Platform observability
