Wildcards → DAG → dry-run

You request an output file. Snakemake recurses back through rules until it hits files that already exist.

The DAG is built statically — every job is known up-front.

# show the full plan before running
snakemake bam/sample42.bam --dry-run

# emit Graphviz
snakemake --rulegraph | dot -Tpng > rules.png

All executors, all remote-storage backends, all software-deployment options shipped in one package.

  •   Report — rocrate, nanopub …
  •   Scheduler — greedy, ilp, milp

What actually matters in v9.x

  New capabilities

  • Pluggable metadata persistence — .snakemake/ to files or DB
  • Cross-workflow caching with storage-plugin checksums
  • Named multi-output caching
  • Logger plugins — observability (snkmt SQLite/TUI)
  • Report plugins — RO-Crate (FAIR) · Nanopub

  Quality-of-life

  • profile.yaml is the new default filename
  • Pass a YAML file directly (not just a directory)
  • subpath(with_suffix=...) helper
  • Auto-detected network FS type
  • Plugins with no settings auto-deploy

  9.20 footgun: runtime values are now minutes, not seconds.

Migration footguns

  •   dynamic() outputs → use checkpoints
  •   version: directive → use conda: / container:
  •   subworkflow: → module: + use rule * from foo as foo_*
  •   from snakemake.remote.* → storage directive
  •   CI must pip install snakemake-executor-plugin-slurm explicitly
  •   v9.20: audit runtime: values — seconds became minutes
  •   v7 profiles reference removed flags — silently broken on v8

vs

Snakemake vs Nextflow

Strictly objective · pick on fit, not on taste

The deepest difference — dataflow

  Snakemake — pull

Target-driven, Make-style.

“What file do I want?”

  • Request output → recurse back
  • Static DAG, built up-front
  • --dry-run shows the full plan
  • Conditional flow via Python / checkpoints

  Nextflow — push

Channel-driven, Kahn / CSP-style.

“What stream into what process?”

  • Channels emit records
  • Processes fire on input availability
  • Dynamic DAG, materializes at runtime
  • Branching native via operators

Resume / cache — myth-buster

  Snakemake

File timestamps + tracked metadata in .snakemake/.

Triggers: --rerun-triggers {mtime, params, input, software-env, code}.

Make pitfall: touching an input invalidates downstream.

  Nextflow

Hash in .nextflow/cache/ (LevelDB).

Hashes script + input attributes (path/size/mtime) by default — not contents.

cache 'deep' → true content hash · cache 'lenient' for shared FS.

Warning

“Nextflow -resume is content-hashed” — partially false. Default = file attributes incl. mtime. Both tools are sensitive to FS metadata. Neither is magic.

1 · Caching — workflow + containers

  Workflow output cache 

export SNAKEMAKE_OUTPUT_CACHE=\
  /scratch_cached/<group>/snakemake_cache

Per rule:

rule index_ref:
    output: "ref.fa.bwt"
    cache: True   # shared across users

Computed indexes (BWA, STAR, ref dicts) reused across users → minutes saved per run.

  Container & conda cache 

# profile
conda-prefix:     /g/<group>/shared/conda
apptainer-prefix: /g/<group>/shared/apptainer

  Group-writable, chmod 2775 (setgid) → no per-user re-solves.

  Pre-warm: snakemake --conda-create-envs-only

2 · Storage — staging via fs plugin

profile/config.yaml
executor: slurm
default-storage-provider: fs                       # auto-stage to scratch
local-storage-prefix: /scratch/$USER/snakemake/<wf>
shared-fs-usage:                                   # what stays on shared FS
  - persistence
  - software-deployment
  - sources                                        # NOT input-output!
Data Tier Why
Reference genomes · indexes Cached parallel FS Read 100×
BAM / CRAM intermediates Parallel FS Sequential writes
Conda · containers Parallel FS (shared) Multi-user reuse
Sorting · temp buffers Local scratch Ultra-fast, per-job

3 · Job grouping + arrays

rule trim:
    input:  "fastq/{s}.fq.gz"
    output: "trim/{s}.fq.gz"
    group:  "preproc"   # ◀ same group

rule align:
    input:  "trim/{s}.fq.gz"
    output: "bam/{s}.bam"
    group:  "preproc"   # ◀ same SLURM job
# profile — array submissions
executor: slurm
slurm-job-array: true
jobs: 500
max-jobs-per-second: 10

  Group: one sbatch instead of two per sample · shared scratch.

  Array: batch homogeneous jobs into sbatch --array=… · single squeue entry.

  Combine both → array of grouped jobs.

  Heterogeneous resources → keep arrays separate.

4 · EESSI — env-modules everywhere

EESSI = European Environment for Scientific Software Installations — a CernVM-FS stream of pre-built scientific software, mountable on any HPC.

source /cvmfs/software.eessi.io/versions/2023.06/init/bash
module load BWA SAMtools STAR

Per rule:

rule align:
    envmodules: "BWA/0.7.17", "SAMtools/1.18"
    shell: "bwa mem ... | samtools sort ..."

Invoke with --sdm env-modules.

  No conda solve · no image pull

  Identical tool versions across sites

  Reproducibility comparable to containers

eessi.io

Bonus · dependency cooldowns

  Why

Malicious PyPI / conda releases are usually yanked within hours to days. Tell your resolver to ignore versions published in the last N days → compromised releases disappear before your build ever sees them. Bonus: dampens surprise breakage.

  pip 26.1 (Apr 2026) 

pip install --uploaded-prior-to=P7D requests
  • 26.0 → absolute date · 26.1 → relative duration
  • Also in pip.conf
  • Relies on PEP 700 upload time

  Pixi · exclude-newer 

[workspace]
exclude-newer = "14d"
channels = [
  "conda-forge",
  { channel = ".../internal",
    exclude-newer = "0d" }
]

[exclude-newer]
openssl = "0d"   # bypass for CVE

Same concept as uv/rattler · 7 days is the commonly cited default · Richard Si’s writeup

A minimal end-to-end Snakefile

Snakefile
configfile: "config/config.yaml"

SAMPLES = config["samples"]

rule all:
    input: expand("results/{sample}.vcf", sample=SAMPLES)

rule align:
    input:  "data/{sample}.fq.gz"
    output: "results/{sample}.bam"
    threads: 8
    resources: mem_mb=16_000, runtime=120     # ⚠ minutes since 9.20
    conda:   "envs/bwa.yaml"
    group:   "per_sample"
    shell:   "bwa mem -t {threads} ref {input} | samtools sort -o {output}"

rule call_snvs:
    input:  "results/{sample}.bam"
    output: "results/{sample}.vcf"
    container: "docker://broadinstitute/gatk:4.5"
    group:  "per_sample"
    shell:  "gatk HaplotypeCaller -I {input} -O {output}"

A full EMBL HPC profile

profile/config.yaml
executor: slurm
jobs: 500
max-jobs-per-second: 10
software-deployment-method: [conda, apptainer]

# software & cache
conda-prefix:     /g/<group>/shared/conda
apptainer-prefix: /g/<group>/shared/apptainer

# storage staging
default-storage-provider: fs
local-storage-prefix: /scratch/$USER/snakemake/<wf>
shared-fs-usage:
  - persistence
  - software-deployment
  - sources

# scheduler hygiene
slurm-job-array: true
slurm-efficiency-report: true
slurm-efficiency-threshold: 0.8
retries: 2
export SNAKEMAKE_OUTPUT_CACHE=/scratch_cached/<group>/snakemake_cache
snakemake --profile profile/ --jobs 500

When does each fit?

  Snakemake fits when…

  • Team is Python-native
  • Pipeline is file / target-driven
  • You want the DAG up-front
  • Debugging needs interactive Python
  • One Snakefile, readable end-to-end

  Nextflow fits when…

  • Team has Groovy / JVM people
  • Pipeline is stream / event-driven
  • AWS Batch or Fusion matter
  • You want nf-core off-the-shelf
  • You want Seqera Platform observability
