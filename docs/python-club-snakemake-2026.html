Storage — in practice

  Concrete: a reference + run from S3 

storage s3_aws:
    provider="s3",
    max_requests_per_second=10,
    endpoint_url="https://s3.eu-central-1.amazonaws.com"

rule align:
    input:
        reads = storage.s3_aws("s3://my-bucket/run42/{sample}.fq.gz"),
        ref   = storage.s3_aws("s3://refs/hg38.fa")
    output:
        storage.s3_aws("s3://my-bucket/run42/{sample}.bam")
    threads: 8
    conda:     "envs/bwa.yaml"
    container: "docker://biocontainers/bwa:0.7.17"
    shell:
        "bwa mem -t {threads} {input.ref} {input.reads} | "
        "samtools sort -o {output}"

snakemake \

Software deployment — one flag

--use-conda
--use-singularity
--use-envmodules

v8 / v9 — one flag 

--sdm conda         # conda env per rule
--sdm apptainer     # Apptainer/Singularity
--sdm env-modules   # HPC env-modules (EESSI…)
--sdm conda apptainer    # compose

Per-rule directives — all three are supported simultaneously:

rule align:
    conda:      "envs/bwa.yaml"                  # ◀ conda
    container:  "docker://biocontainers/bwa:0.7.17"  # ◀ container
    envmodules: "BWA/0.7.17", "SAMtools/1.18"    # ◀ env-modules
    shell: "bwa mem ..."

  --conda-frontend mamba removed — libmamba is the default solver · Pixi backend on the roadmap.

Plugins

  • pluggable metadata persistence — .snakemake/ to files or DB

  • runtime values in profiles/CLI are now minutes, not seconds

Migration footguns

  •   dynamic() outputs → use checkpoints
  •   version: directive → use conda: / container:
  •   subworkflow: → module: + use rule * from foo as foo_*
  •   from snakemake.remote.* → storage directive
  •   CI must pip install snakemake-executor-plugin-slurm explicitly
  •   v9.20: audit runtime: values — seconds became minutes
  •   v7 profiles reference removed flags — silently broken on v8

Snakemake vs Nextflow

Strictly objective · pick on fit, not on taste

The deepest difference — dataflow

  Snakemake — pull

Reason from the end.

rule all:
    input: "vcf/cohort.vcf"  # ◀ the target

rule call:
    input:  "bam/{s}.bam"
    output: "vcf/{s}.vcf"

rule align:
    input:  "fq/{s}.fq.gz"   # ◀ leaf
    output: "bam/{s}.bam"

“To produce cohort.vcf I need bam/*.bam, which needs fq/*.fq.gz.” Static DAG.

  Nextflow — push

Reason from the start.

workflow {
  Channel.fromFilePairs(
    'fq/*_{1,2}.fq.gz'      // ◀ the source
  ) | ALIGN | CALL | view
}

process ALIGN { /* fq → bam */ }
process CALL  { /* bam → vcf */ }

“FASTQ pairs emit into a channel → ALIGN consumes them → CALL consumes ALIGN’s output…” Dynamic DAG.

Resume / cache — myth-buster

  “My input file changed. Will the job rerun?”

Warning

“Nextflow -resume is content-hashed” — partially false. Default hashes file attributes (mtime included). Content hashing is opt-in via cache 'deep'.

Software & containers

  Capability Snakemake   Nextflow / nf-core
  Per-rule env conda: + container: + envmodules: conda + container directive
  Compose --sdm conda apptainer engine + conda
  Curated registry snakemake-wrappers BioContainers · mulled · Seqera Containers
  Build on demand — Wave
  POSIX over object storage — Fusion

Wave — Seqera’s container-provisioning service. Takes a conda spec attached to a process, builds an OCI container on demand with that environment, caches it in a registry. Supports amd64 + arm64. Apache-2.0, open source.

Fusion — a virtual POSIX layer that lets processes read/write S3, GCS or Azure Blob as if they were a mounted directory. Avoids stage-in/stage-out copies on cloud. Commercial, part of Seqera Platform.

1 · Caching — workflow + containers

  Workflow output cache 

export SNAKEMAKE_OUTPUT_CACHE=\
  /scratch_cached/<group>/snakemake_cache

Per rule:

rule index_ref:
    output: "ref.fa.bwt"
    cache: True   # shared across users

Computed indexes (BWA, STAR, ref dicts) reused across users → minutes saved per run.

  Container & conda cache 

# profile
conda-prefix:     /g/<group>/shared/conda
apptainer-prefix: /g/<group>/shared/apptainer

  Group-writable, chmod 2775 (setgid) → no per-user re-solves.

  Pre-warm: snakemake --conda-create-envs-only

2 · Storage — staging via fs plugin

profile/config.yaml
executor: slurm
default-storage-provider: fs                       # auto-stage to scratch
local-storage-prefix: /scratch/$USER/snakemake/<wf>
shared-fs-usage:                                   # what stays on shared FS
  - persistence
  - software-deployment
  - sources                                        # NOT input-output!
Data Tier Why
Reference genomes · indexes Cached parallel FS Read 100×
BAM / CRAM intermediates Parallel FS Sequential writes
Conda · containers Parallel FS (shared) Multi-user reuse
Sorting · temp buffers Local scratch Ultra-fast, per-job

3 · Job grouping — map · sort · dedup · index → one job

rule bwa:
    input:  "fq/{s}.fq.gz"
    output: temp("bam/{s}.sort.bam")
    group:  "alignment_per_cell"

rule sort:
    input:  "bam/{s}.sort.bam"
    output: temp("bam/{s}.sorted.bam")
    group:  "alignment_per_cell"

rule dedup:
    input:  "bam/{s}.sorted.bam"
    output: temp("bam/{s}.dedup.bam")
    group:  "alignment_per_cell"

rule index:
    input:  "bam/{s}.dedup.bam"
    output: "bam/{s}.bam.bai"
    group:  "alignment_per_cell"
  1 SLURM job per sample
bwa mem
↓
samtools sort
↓
mark_duplicates
↓
samtools index

  Shared scratch · zero stage-in between steps · temp() cleaned at group end

4 · Job arrays — parallel inside one submission

profile/config.yaml
executor: slurm
slurm-array-jobs: all      # all eligible rules

group-components:

5 · EESSI — env-modules everywhere

EESSI = European Environment for Scientific Software Installations — a CernVM-FS stream of pre-built scientific software, mountable on any HPC.

source /cvmfs/software.eessi.io/versions/2023.06/init/bash
module load BWA SAMtools STAR

Per rule:

rule align:
    envmodules: "BWA/0.7.17", "SAMtools/1.18"
    shell: "bwa mem ... | samtools sort ..."

Invoke with --sdm env-modules.

  No conda solve · no image pull

  Identical tool versions across sites

  Reproducibility comparable to containers

Bonus · dependency cooldowns

  Why: malicious PyPI / conda releases are usually yanked within hours to days. Tell your resolver to ignore versions published in the last N days → compromised releases disappear before your build sees them.

Real EMBL profile — part 1

config.v9+.yaml — execution & resources
executor: slurm
jobs: 150                       # max concurrent SLURM jobs

# Default resources allocated to every rule unless overridden
default-resources:
  - mem_mb=500
  - runtime=600                 # ⚠ pre-9.20 = seconds; from 9.20 = minutes
  - constraint=''               # SLURM --constraint

# Per-rule resource overrides — pin the alignment group to milan nodes
# (sambamba mark_duplicates needs AVX2 only on milan)
set-resources:
  ashleys_bwa_strandseq_to_reference_alignment: { constraint: milan }
  ashleys_samtools_sort_bam:                    { constraint: milan }
  ashleys_mark_duplicates:                      { constraint: milan }
  index_input_bam:                              { constraint: milan }

# Scheduler hygiene
max-jobs-per-second: 10
max-status-checks-per-second: 10
latency-wait: 60
local-cores: 32

# Fault tolerance
keep-going: true
rerun-incomplete: true
retries: 4                      # leverages attempt-based memory scaling

When does each fit?

  Snakemake fits when…

  • Team is Python-native
  • Pipeline is file / target-driven
  • You want the DAG up-front
  • Debugging needs interactive Python
  • One Snakefile, readable end-to-end

  Nextflow fits when…

  • Team has Groovy / JVM people
  • Pipeline is stream / event-driven
  • AWS Batch or Fusion matter
  • You want nf-core off-the-shelf
  • You want Seqera Platform observability
